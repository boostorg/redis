= Multi-threading

* Before doing multi-threading, think twice if you need it.
  You can get very far with single-threaded I/O event loops.
  Recall that all functions in Boost.Redis are async,
  so multiple tasks may run concurrently even if using a single thread.
* If you are performing computation intensive tasks, consider deferring
  these to a thread pool, and keeping the I/O event loop single-threaded.
* Multiple threads performing I/O require synchronization that has overhead.
  Always measure performance before switching to multi-threading.

== Asio multi-threading refresher

Boost.Redis follows Asio's conventions regarding multi-threading:

* I/O objects (like `connection`) don't have any built-in synchronization
  support. This way, no overhead in single-threaded cases. It is
  your responsibility, as a user, to add proper guards.
* A multi-threaded application is running an execution context with
  many threads running handlers. Easiest way is using `thread_pool` (TODO: insert example).
* The way to ensure thread-safety is by using strands. A strand is a special executor
  that ensures that no two handlers run in parallel, preventing race conditions.
* You need a strand if two handlers may run in parallel and access
  a shared data structure. Some examples (use a tcp socket for these):
  ** Serial socket read, then write: no strand needed here because all operations
     are strictly sequential.
  ** Parallel socket read and write: a strand is needed here (show tha race-y example,
     then the correct example. Use make_parallel_group).
  ** Read with timeout: a strand is needed here (show tha race-y example,
     then the correct example. Use make_parallel_group).
* Strands have shared ownership. Once you create a strand, all subsequent copies
  refer to the same underlying strand. Strands created by different `asio::make_strand`
  calls are however different. Handlers submitted to them are allowed to run
  in parallel (as acquiring different instances of `std::mutex` would do). (show example).
* Never use `std::mutex` or `std::condition_variable` - these block
  the calling thread, which prevents it from running other tasks. This would be akin
  to calling a blocking function - against the async rules!
* Strands should not be used to synchronize tasks. E.g. to signal the completion
  of an event, or to make one task suspend until another finishes.
  This should be done using channels and timers. Put it another way,
  if your program uses a single-threaded I/O context, and it still uses
  strands, you're doing it wrong.
* It's easy to get it wrong. Use -fsanitize=thread with your code
  and perform a stress test to double-check.

Strands serialize handlers, not tasks. For example, if you run the following
in a connection that uses a strand:

```
// TODO: sanitize this
make_parallel_group(
  conn.async_exec(req1, res1),
  conn.async_exec(req2, res2)
);
```

Both requests will be sent to the server as soon as possible,
and may be pipelined together (as in the single-threaded case).
Concretely, a strand **does not cause req2 to wait for req1 to be
completed before it is sent to the server**. It is the handlers that
get serialized, not the requests.
